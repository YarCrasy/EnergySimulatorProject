Testing

Tests de backend y frontend

El proyecto EnergySimulator cuenta con una batería de pruebas tanto en el backend Java/Spring como en el frontend React. Las pruebas permiten validar que la API funcione correctamente, que los componentes visuales se rendericen adecuadamente y que los flujos críticos —autenticación, CRUD de proyectos, simulación— se comporten según lo esperado antes de integrar cambios en la aplicación web y Android.

Backend

Las pruebas del backend se realizaron mediante Postman, una herramienta de testing de API que permite enviar peticiones HTTP y verificar las respuestas de los endpoints REST del servidor.

Se hicieron pruebas manuales de los verbos GET, POST, PUT y DELETE sobre las principales clases del simulador (usuarios, proyectos, consumos), comprobando que los endpoints responden correctamente con los códigos HTTP esperados (200 OK, 201 Created, 404 Not Found, etc.).

  • Pruebas de creación (POST): envío de datos en formato JSON al endpoint correspondiente y verificación de que el recurso se crea con su ID autogenerado.
  • Pruebas de consulta (GET): obtención de la lista de recursos y verificación de que los datos devueltos coinciden con los almacenados.
  • Pruebas de actualización (PUT): modificación de un recurso existente enviando los nuevos datos en el body y comprobando la respuesta con los cambios aplicados.
  • Pruebas de eliminación (DELETE): borrado de un recurso por su ID y confirmación mediante el código de respuesta y los datos del elemento eliminado.
  • Importante: al enviar datos en Postman, debe seleccionarse la opción Body → raw → JSON para que el servidor interprete correctamente la información.

Frontend

El frontend web usa Vitest como test runner, junto con React Testing Library para la validación de componentes y jsdom como entorno de navegador simulado. Los tests se organizan en tres categorías: lógica de autenticación, llamadas a la API e interacción con componentes visuales.

cd web
npm run test
npm run test:watch
npm run test:coverage

Los tests siguen el patrón Arrange, Act, Assert (AAA) y utilizan mocks para aislar las dependencias externas (axios, react-router-dom, localStorage).

La cobertura se genera automáticamente con npm run test:coverage y el informe HTML queda disponible en la carpeta web/coverage/.

Tests de autenticación — tests/Logics/

Los tests de lógica cubren el flujo completo de inicio de sesión, el comportamiento del proveedor de contexto de autenticación y la seguridad frente a ataques de inyección y manipulación de sesión.

Login — Logics/Login/login.flow.test.tsx

Este archivo verifica el flujo completo de la página de inicio de sesión, desde el relleno de credenciales hasta la redirección según el rol del usuario.

  • Redirección a administración: cuando el backend responde con rol admin, la navegación redirige a /administration/users.
  • Redirección a proyectos: cuando el rol es user, redirige a /projects.
  • CTA del simulador: si el usuario viene desde el botón "Probar simulador" (redirectToSimulator: true), tras autenticarse se crea un proyecto automáticamente y se navega a /simulator/{id}.
  • Error de creación de proyecto: si createProject falla, se muestra una alerta y se redirige al panel por defecto según el rol.
  • Error de login: cuando las credenciales son inválidas, se muestra una alerta con el mensaje del backend y no se redirige.
  • Prevención de doble envío: mientras isSubmitting está activo, el botón muestra "Ingresando..." y está deshabilitado, bloqueando submits adicionales.
  • Rol indefinido: si el rol no es admin, se aplica el fallback /projects por defecto.
  • Navegación a registro: el botón "Crear cuenta" navega correctamente a /register.
  • Campos vacíos: si FormData.get devuelve null para email o password, se envían cadenas vacías.

AuthProvider (comportamiento) — Logics/Login/authContext.behavior.test.tsx

Prueba el proveedor de contexto de autenticación en condiciones normales, verificando la hidratación desde localStorage, la persistencia tras login exitoso y la limpieza al cerrar sesión.

  • Estado inicial: sin sesión previa, loading es false y user/token son null.
  • Hidratación desde localStorage: cuando hay datos válidos guardados, el provider los restaura automáticamente.
  • Sesión corrupta: si el JSON guardado es inválido, se descarta y se limpia el almacenamiento.
  • Login exitoso — mapeo de roles: admin: false se traduce a rol user; admin: true se traduce a rol admin.
  • Respaldo de nombre: si el payload no incluye name, se usa fullName; si ninguno está presente, se usa cadena vacía.
  • Login fallido: si el backend responde con un mensaje de error, se propaga; si no hay detalle, se usa el mensaje genérico "Usuario o contrasena incorrectos".
  • Logout: limpia el usuario, el token y los datos persistidos en localStorage.

AuthProvider (seguridad) — Logics/Security/authContext.security.test.tsx

Validaciones de seguridad sobre el contexto de autenticación para prevenir XSS, manipulación de roles y datos corruptos.

  • Sanitización XSS: al hidratar desde localStorage o al recibir datos del backend, se eliminan etiquetas HTML (<script>) y prefijos peligrosos como javascript:.
  • Prevención de escalación de privilegios: roles manipulados como super-admin se normalizan a user.
  • Sesión sin id: si falta el campo id, la sesión se descarta por completo.
  • Valor no objeto: si localStorage contiene un valor no objeto (p.ej. un string plano), se descarta.
  • Campos no string: nombres numéricos o emails nulos se normalizan a cadena vacía.
  • Login sin token: si el backend responde sin token ni usuario, no se persiste la sesión y se lanza un error controlado.

Configuración y troubleshooting

Los tests frontend se configuran desde web/vite.config.ts con el entorno jsdom y el archivo de setup tests/setupTests.ts que importa los matchers de @testing-library/jest-dom/vitest y ejecuta cleanup tras cada prueba.

// web/vite.config.ts (fragmento relevante)
test: {
  environment: "jsdom",
  globals: false,
  include: ["tests/**/*.test.ts", "tests/**/*.test.tsx"],
  setupFiles: ["./tests/setupTests.ts"],
  clearMocks: true,
  restoreMocks: true,
}

Problemas comunes y solución:

  • Failed to resolve import "@/...": revisar alias en web/vite.config.js y la ruta exacta (mayúsculas/minúsculas).
  • esbuild build() is unavailable in this environment: ejecutar tests fuera del sandbox del IDE.
  • ReferenceError: fetch is not defined: en este proyecto se mockea @api/api (axios), no fetch.
  • Error de entorno DOM: confirmar environment: 'jsdom' y setupFiles en web/vite.config.js.
